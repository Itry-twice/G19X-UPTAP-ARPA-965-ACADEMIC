# ADR-0001 — Arquitectura de microservicios

- **Estado:** Aceptado
- **Fecha:** 2026-09-09

## Contexto

El proyecto requiere una plataforma modular (onboarding + IA + tickets) que pueda crecer. Se evalúa entre un monolito y microservicios.

## Decisión

Se adopta una arquitectura de microservicios con 5 componentes: Web/BFF, AuthService, OnboardingService, HrService y AI Service.

## Consecuencias

- Separación clara de responsabilidades y despliegue independiente.
- Mayor complejidad operativa (redes, health checks, comunicación interna).
- Cada servicio se escala y versiona de forma independiente.

# ADR-0002 — Lenguajes y frameworks

- **Estado:** Aceptado

## Contexto

Se requieren servicios de backend, un BFF con frontend integrado y un servicio de IA.

## Decisión

- Backend y BFF: .NET 9 (ASP.NET Core).
- Frontend: Razor Pages + JavaScript (sin React).
- IA: Python + FastAPI + LangGraph + LangChain.
- LLM: Groq, modelo `openai/gpt-oss-20b`.

## Consecuencias

- Consistencia con el stack definido en el proyecto.
- El BFF integra el frontend y evita exponer infraestructura al navegador.

# ADR-0003 — Autenticación con JWT + sesiones

- **Estado:** Aceptado

## Contexto

El navegador solo habla con el BFF; los microservicios son internos. Se necesita identidad y sesión seguras.

## Decisión

- AuthService emite un access token (JWT firmado con secreto compartido) y un refresh token opaco almacenado (hash) en `auth.sessions`.
- El BFF guarda ambos en cookies HttpOnly/Secure/SameSite.
- El BFF propaga el JWT a los microservicios vía `Authorization: Bearer`.
- Cada servicio valida la firma JWT; el AI Service verifica la firma (confía en claims emitidos por el backend) sin gestionar usuarios.

## Consecuencias

- Sesiones revocables (logout invalida refresh).
- No se requiere sesión de servidor en el BFF.

# ADR-0004 — Esquema de base de datos gestionado por migraciones SQL

- **Estado:** Aceptado

## Contexto

Tres servicios .NET y un servicio Python comparten PostgreSQL con pgvector. Coordinar migraciones EF Core concurrentes es frágil.

## Decisión

- El esquema se define mediante scripts SQL versionados en `infrastructure/postgres/init/` aplicados por `docker-entrypoint-initdb.d`.
- Los servicios .NET usan EF Core (Npgsql) como capa de acceso sobre el esquema existente (modelo database-first), sin `EnsureCreated`.
- pgvector y los roles/políticas RLS se crean en el mismo init.

## Consecuencias

- Orden de aplicación determinista y reproducible.
- Una única fuente de verdad para el esquema.

# ADR-0005 — Row Level Security por rol de base de datos y contexto de usuario

- **Estado:** Aceptado

## Contexto

Se exige que los datos se restrinjan en base de datos, no solo en la aplicación.

## Decisión

- Cada servicio usa su propio rol de BD (`svc_auth`, `svc_onboarding`, `svc_hr`, `svc_ai`).
- Las tablas usan RLS. El filtro por propietario se aplica mediante la variable de sesión `app.user_id`, establecida por el servicio desde los claims JWT en cada conexión.
- Los roles RRHH/Admin acceden mediante políticas que evalúan `app.role`.

## Consecuencias

- Defensa en profundidad; el acceso indebido se bloquea incluso si la capa de aplicación falla.

# ADR-0006 — Abstraction del proveedor LLM

- **Estado:** Aceptado

## Contexto

Se usará Groq para el MVP, pero se desea cambiar de proveedor sin reescribir el sistema.

## Decisión

- El AI Service define una interfaz `LLMProvider` (chat + streaming). La implementación `GroqProvider` es la única para el MVP.
- El modelo se configura vía `GROQ_MODEL` (por defecto `openai/gpt-oss-20b`).

## Consecuencias

- Cambiar de proveedor implica implementar una clase, no reescribir el flujo.
